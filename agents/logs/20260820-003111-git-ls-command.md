## Objective

Build a `git ls` command (a `git-ls` executable on PATH, like `scripts/git-stack-*`)
that lists the tree of the current checkout (HEAD):

- `git ls [PATH...]` ≡ `gitfs ls HEAD [PATH...]` (names only)
- `git ls -l|--long [PATH...]` ≡ `gitfs ls HEAD --blame=N [PATH...]`
- `N` defaults to 1000, configurable via `git config gitls.blameLimit`
- Remaining args (paths, `--blame=X`, `--sparse`) pass through to gitfs ls

Decisions confirmed with the user:
- `-l` toggles blame (plain `git ls` is names-only)
- config key is `gitls.blameLimit`

## Obstacles

- **Issue:** Initial plan refactored `cmd/gitfs/main.go` into a shared `internal/cli`
  package so a Go `cmd/git-ls` binary could reuse the ls command.
  **Resolution:** User steered to the simpler design before any code was moved:
  `git ls` only re-exposes the gitfs CLI through a different interface, so a bash
  wrapper in `scripts/` (matching the `git-stack-*` convention) is sufficient and
  needs no refactor.
- **Issue:** After the bash wrapper landed and passed tests, the user asked for the
  same thing as a Go binary — "basically copy the gitfs ls subcommand
  implementation over, no refactoring of any existing code".
  **Resolution:** Replaced `scripts/git-ls` with `cmd/git-ls/main.go`: the ls
  subcommand code copied verbatim from `cmd/gitfs/main.go` (cat and REF completion
  dropped), REF fixed to HEAD, and `-l` wired to `--blame=$(git config
  gitls.blameLimit || 1000)` in the flag-handling switch. The existing integration
  tests were retargeted from the script to `bin/git-ls` first (red), then the
  binary made them pass unchanged (green). Duplication is documented in the file
  header, README, and CLAUDE.md as deliberate.
- **Issue:** macOS `/bin/bash` is 3.2, where `"${arr[@]}"` on an empty array errors
  under `set -u`. (Only relevant to the since-removed bash wrapper.)
  **Resolution:** Used the `${arr[@]+"${arr[@]}"}` expansion guard in the wrapper.

## Outcome

- `cmd/git-ls/main.go`: `git ls` ≡ `gitfs ls HEAD`; `-l`/`--long` ≡
  `gitfs ls HEAD --blame=$(git config gitls.blameLimit || 1000)`. Explicit
  `--blame[=LIMIT]` wins over the config default. Bad config values fail via
  git's own "bad numeric config value"; negatives are rejected by the binary
  itself. The ls implementation (table rendering, blame columns, GitHub
  hyperlinks, glob expansion, repo discovery) is a verbatim copy of
  cmd/gitfs's ls — duplication deliberate, documented in the file header,
  README, and CLAUDE.md.
- `tests/integration/test_git_ls.sh` covers plain/long output parity with
  `gitfs ls HEAD`, path passthrough, config override, invalid config, explicit
  `--blame` precedence, bare `--blame` (unbounded), and dispatch via real
  `git ls` — all on both backends.
- Root Makefile `install` installs both binaries; integration Makefile builds
  both.
- Nothing committed; left for the user to commit.

## Insights

- `git config --type=int --get --default=1000 <key>` gives config-with-default
  plus validation in a single call — no error-code sniffing needed.
- `git <cmd> --help` is intercepted by git itself (shows a man page), so wrapper
  help is only reachable as `git-ls --help`; worth documenting inside the script.
